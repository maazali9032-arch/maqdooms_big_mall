# Positive SP before production barcode generation — 20 October 2026

For new shop-production receipts, every piece needs a positive selling price before its barcode is generated, matching the customer-finished-garment requirement. Whole-batch receipt remains the rule; this change does not introduce partial receipt.

Finished Products scanning now identifies/reads a production document without receiving, completing the job or generating piece barcodes. Unreceived orders show each piece's product, design, size and initial SP input. Apply SP to all fills the inputs, with individual overrides allowed. Confirmation is disabled until every value is valid and positive. Both receiving and finished-price permissions are required. On confirmation the server receives the full batch, records costing, saves reviewed piece prices and generates the pieces/barcodes in the same transaction. A failure rolls back all these changes. Unknown results lock the fields/scanner and retry the original request and prices.

Migration `20261020000500_production_sp_before_barcode.sql` / Drizzle `0072_production_sp_before_barcode.sql` adds private `validate_production_piece_prices`, private `complete_production_batch_priced` and authenticated `receive_production_barcode_priced(uuid,text,jsonb)`. Prices are canonicalized by piece number and captured in the receipt/request payload. Missing, duplicate, non-integer, out-of-range, partial and zero/negative values fail. Old `complete_production_batch` cannot create new unpriced pieces; historical exact retries remain available. Old scanner calls can reopen existing receipts but cannot generate new unpriced pieces. The legacy Owner allocation API also requires `sp_paise` for every supplied piece before generation; its optional screen supplies those prices.

Existing barcodes, stock, historical receipts and SP records are preserved. Existing pieces can still be opened, priced and reprinted through their established controls. No missing historic price is fabricated. Customer-finished items already require a positive SP and are unchanged. Initial prices follow the current configured POS GST price mode; no new tax logic is introduced.

The migration is applied live following an actual-schema rollback dry run and post-commit definition/permission checks. Business fingerprints include barcodes, finished pieces, prices/reviews and receipt records, and matched before/after. No production test garments or sales were posted. The application release is pushed with this change; served-code verification is separate from a real physical-printer/user acceptance test.

Verification: complete disposable migration replay; `scripts/production-priced-receipt-cases.mjs` (permissions, no barcode on invalid prices, different positive SP per piece, reviewed prices, exact retry and historical scan reopening); `scripts/production-priced-receipt-ui-test.mjs <Playwright module path>` (read-only scan, input gating, per-piece overrides, mobile layout and locked retries); TypeScript, scoped lint, formatting and production build. Older historical tests that assume no-price receipt must be updated to supply prices before using the new workflow.

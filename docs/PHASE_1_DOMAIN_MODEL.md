# Phase 1 — Database / Domain Model

Business authority: `MAQDOOMS_Big_Mall_ERP_Implementation_Master_Plan.md`. Implementation record: `MAQDOOMS_Big_Mall_ERP_Implementation_History.md`. This document describes the migration contract, not completed operational workflows.

## Migration and deployment boundary

- Canonical migration: `supabase/migrations/20261003000000_phase1_domain_model.sql`.
- Equivalent Lovable/Drizzle migration: `drizzle/migrations/0010_phase1_domain_model.sql`, appended at journal index 10. These are two execution-path copies of **one logical migration**. Apply the appropriate chain once, not both to one database.
- Existing migrations, demo seed, application code, Auth flows and legacy RPCs are preserved. `drizzle/schema.ts` remains intentionally empty; do not use schema generation/push to replace the SQL migration chain. Older snapshots are historical, not the current schema contract.
- Local replay was tested in disposable PostgreSQL. The linked/production database was not changed; deployed parity and application of the new migration are not asserted.
- The migration is transactional. New objects are intentionally not idempotent: an applied migration must be tracked by the chosen migration runner, not silently rerun. Production rollout must inspect deployed parity first and use the version-controlled file; never manually reproduce its statements.

## Existing columns, constraints, indexes and functions

- `profiles.id` now references `auth.users.id`; `user_roles.user_id` and `user_permission_overrides.user_id` reference profiles. These FKs are initially NOT VALID to preserve old orphans, which are flagged. Each constraint is validated automatically if its existing rows are clean. An unvalidated FK still enforces new writes; reconciliation/validation of existing orphans remains outstanding where found.
- `thaans.fabric_stock_id` is nullable during compatibility transition. The composite FK requires its fabric/batch to match the parent, and a paired (id,fabric_stock_id) unique key supports traceable item references. Legacy `barcode` becomes nullable but retains its uniqueness; every row must have either a historical label or a Fabric Stock parent. Current original length/CP/SP/status semantics and RPCs are unchanged.
- `materials.active` is added with true default; all original units, quantities and financial values stay intact.
- Primary/unique keys index identities, codes, barcode kind references, revisions, piece numbers and composite relationship targets. Additional indexes cover location parents, active root uniqueness, section/factory grouping, current Tailor assignment, receiving batch/stock parents, customer/assignment job lookups, issue/requirement/transfer/order child lookups, Finished Product location/status, inventory item/source/destination/time queries, cost-version lines, genealogy by job and audit entity/time. Transfer/issue event references have unique partial indexes to prevent repeated posting of one line. Exact index names are in SQL.
- Six trigger functions: `validate_showroom_parent`, `validate_finished_product`, `validate_production_quantity`, `validate_domain_links`, `protect_domain_identity`, `reject_domain_history_rewrite`. They enforce model relationships/history only. No stock balance, receiving, scan/print, sale, transfer, material issue, production completion or reporting RPC is added.
- History triggers prohibit UPDATE/DELETE for barcodes, financial/charge versions, order financial snapshots, new inventory movements, costs/allocations/genealogy, material issues/lines and audit records. New versions/correction events preserve past facts.

## Backfill and preservation

1. For every existing non-null Fabric + Batch pair, create one `legacy_pending` Fabric Stock and a stable fabric-kind identifier (`FAB-` + UUID). Link the known internal Thaans to it; do not change old labels or values.
2. Copy CP/SP to revision 1 **only** when every member has the same non-null, nonnegative value. All-null SP stays optional. Mixed/missing/invalid CP or differing/partially missing SP is recorded for reconciliation; no averaging, first-row selection or invented price.
3. Flag missing identity and unknown physical locations (retaining rack text as evidence). Keep all legacy ledger rows unchanged; do not invent Workshop opening balances or transfers from rack names.
4. Flag existing tailoring jobs for domain/assignment reconciliation; do not convert null-customer shop work into Production Jobs, create false Factory/Section assignments or import unlinked Tailor names as authenticated people.
5. Flag consumable opening quantities/locations and any Auth/profile/role/override orphans. Retain original data; never delete or silently repair it.
6. Keep the new general ledger empty at migration time. No second copy of legacy quantity is counted. Phase 3 must define an explicit location reconciliation and single-authority cutover before new transactions are enabled.

Migration-generated UUID identifiers are stable after application, but two independent fresh databases receive different UUIDs. No barcode includes CP/SP; SP revisions leave barcode identity unchanged. New manual barcode entry/generation/printing and legacy label transitions are Phase 4.

## RLS and permission boundary

All 34 new public tables have RLS enabled, no browser policies and explicit revocation from PUBLIC/anon/authenticated. The trusted `service_role` receives table privileges; the migration owner retains administrative access. Trigger functions are invoker functions, not new security-definer APIs; direct browser execution is revoked. This is a minimum safe scaffold, **not Phase 2 authorization**. Even an Owner browser session cannot yet use these tables.

Existing role policies, financial grants, RPC security and the Phase 0 CP/helper/cache findings are intentionally unchanged. Phase 2 must fix them, design Owner/Counter/Tailor/Stock Entry workflows, and test PostgREST, view/RPC and inactive/assigned-role behavior. Do not enable the new tables by blanket grants.

## Validation and remaining scope

`scripts/phase1-schema-test.mjs` replays both complete chains independently in disposable PGlite PostgreSQL with minimal mocked Supabase Auth/storage infrastructure. It verifies schema parity, preservation/backfill edge cases, keys/relationships, sealed privileges, append-only history, fixed roots/dynamic floors, separate job domains, ten individual piece records, barcode stability, Workshop-first initial location, component cost storage and genealogy. Its SQL cost aggregation is a **test query**, not an implemented production-cost operation. Fixture values and business entities exist only in disposable tests; the migration seeds no charge/design/product/example production data.

Run with an external temporary runtime:

```powershell
npm install --prefix "$env:TEMP/maqdooms-phase1-pglite" --no-audit --no-fund --package-lock=false @electric-sql/pglite@0.5.8
node scripts/phase1-schema-test.mjs "$env:TEMP/maqdooms-phase1-pglite/node_modules/@electric-sql/pglite/dist/index.js"
```

PGlite is single-connection PostgreSQL; this does not verify live Supabase, PostgREST schema cache, provider infrastructure or multi-connection concurrency. No public/live DB credentials are read by the test script.

The legacy app remains on its previous model: roll barcode lookup, SP-required receiving, Stock Entry CP/SP policies and shared legacy tailoring persist until their phases. New stock entered through old flows after migration is not automatically mapped to Fabric Stock; later receiving cutover must reconcile it. Composite stock identity prevents an already-linked Than's fabric/batch being changed independently; a future controlled correction must handle parent identity coherently. Supabase application types describe legacy APIs; generate/update the new API contract when Phase 2/4 exposes these tables, not by routing current screens to the sealed schema.

Later-phase work remains: operational role access; balance/negative-stock checks and location cutover; one-barcode entry/scan/print; transfers/sales; customer pricing/billing/material transactions; production completion/piece creation service; cost calculation/finalization; Finished Product sales; full audit coverage/reporting; UI and performance. Phase 1 defines their relationships without enabling these workflows.
